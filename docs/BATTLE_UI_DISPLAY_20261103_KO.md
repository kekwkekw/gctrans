# 전투 UI 표시 누락 보완 — 2026-11-03

사용자 화면의 `入魂`과 `必要熱情`은 이미 수집된 원문이며, 기존 UI 사전에도 각각
`입혼`, `필요 열정`이 있다. 이번 누락은 수집 실패가 아니라 **이미지 표시와 실행 중 문자열
조합을 단독 원문의 사전 coverage로 확인할 수 없었던 문제**다.

## 확인한 원인과 수정

| 대상 | 실제 표시 경로 | 수정 |
|---|---|---|
| 入魂 | `NyukonText` 227×52 Sprite → UI Image | 기존 image catalog에 `입혼` PNG 추가 |
| 必要熱情 | `CommandView.ConvertToUnusableText`가 제목·필요 수치·부족 수치를 여러 줄로 조합 → TMP | 기존 `UiTextLookup`에 완성 문자열 1종 추가 |
| 必要HP | 같은 함수가 필요한 HP%와 부족 HP%를 조합 | 같은 경로의 완성 문자열 1종 추가 |
| 残りCT | 같은 함수가 제목·남은 CT 정수를 조합 | 같은 경로의 완성 문자열 1종 추가 |
| 発動 | `TextFusionAcitve` 84×44 Sprite → 입혼 발동 Image | `발동` PNG 추가; 원본 이름의 철자 그대로 사용 |
| 残り / ターン | `TextRest` 55×36 / `TextTurn2` 90×32 Sprite → 전투 점수/턴 Image | `남은` / `턴` PNG 추가 |

예를 들어 실제 버튼 입력 `必要熱情\r\n115\r\n(-14)`는 단독 키 `必要熱情`과 다르다.
prefab의 `Unusable_Text`는 비어 있고 실행 중 값이 들어간다. 반면 같은 asset의
SkillInfo tooltip에는 단독 `必要熱情`이 있어서 기존 조사에서는 그 원문이 조회 성공으로 집계된다.
새 규칙은 `필요 열정\r\n115\r\n(-14)`로 바꾸며 숫자와 줄바꿈은 그대로 보존한다.

PC native 함수 RVA `CA47D0`에서 제목 getter 5개, `Environment.NewLine`, `System.Int32`
인수, 아래 세 서식의 연결을 확인했다. `火傷状態`, `回数不足`은 조합하지 않는 고정 문구로
기존 사전에서 처리되므로 변경하지 않는다.

```text
必要熱情 + newline + integer + newline + (-integer)
必要HP   + newline + integer% + newline + (-integer%)
残りCT   + newline + integer
```

규칙은 전체 문자열에만 일치하고 LF/CRLF를 보존한다. 기존 exact 항목이 우선하며 제목의
검수된 사전 항목이 없으면 번역하지 않는다. 일반적인 줄 단위 치환, 임의 문자열 부분 치환,
새 template framework는 추가하지 않는다. 입력창·Novel·선택지의 기존 보호 경계도 유지한다.
숫자 조합은 DLL 수정이 필요하다. 이미지 4개는 기존 이미지 교체 기능으로 처리한다.

## 함께 조사한 범위

- 확보된 `scene/scene_battle.dmm`의 텍스트 컴포넌트 516개, Sprite 408개, Texture2D 6개,
  UI Image 컴포넌트 2,700개를 대조했다. 전투 atlas 2장의 글자도 시각적으로 확인했다.
- 비어 있지 않은 prefab 문자열은 중복 제외 172종이며 기존 사전 조회 127종, 미일치 45종이다.
  미일치에는 숫자·기호·영문 37종과 기존 제작용 샘플 8종이 포함된다. 이름 길이 샘플,
  설명문 반복 텍스트, 임시 제목, `撃撃` 등의 원문·owner·이전 판정은 로컬 ledger에 보존했다.
  제작용 샘플을 실제 표시 누락으로 간주해 번역하지 않았다.
- 두 설치 PC cache의 해당 Sprite 이름·rect 크기·픽셀이 서로 일치한다. WebGL source와도
  같은 이름·path ID·크기의 UI Image consumer를 확인했다. 원문 census에서 네 이름의 출현은
  이 전투 atlas와 해당 PC cache들로 한정된다. 이 검사는 미취득 미래 asset까지 보증하지 않는다.
- 영어 `TURN`, `NEXT TURN`, `END TURN` 등은 사용자 방침에 따라 유지한다.
- `入魂`, `残り`, `ターン`은 기존 UI exact 번역을 재사용한다. `発動`은 기존 검수 문구
  `発動条件 → 발동 조건`, `発動中の効果 → 발동 중인 효과`의 용어를 재사용한다.
  새로운 문장 의미검수 승인이나 Knowledge 변경으로 기록하지 않는다.

이미지는 built-in image_gen으로 글자를 편집한 뒤 원본 Sprite 크기에 맞춰 합성했다.
입혼 게이지는 지정한 글자 상자 밖 RGBA를 보존한다. 글자 영역의 alpha는 새 글자 모양에 맞춰
변경한다. 발동 배지는 원본 alpha를 유지하되 내부 그림은 생성형 재현이다. 두 독립 글자 이미지는
새 투명 글자 이미지이며 원본 픽셀 보존을 주장하지 않는다. 전체 목록은 161→165개다.
프롬프트·원본/생성본/완성본 SHA-256·consumer·보존 범위는
[이미지 제작 기록](artwork/battle-labels-20261103.json)에 있다.

## 이전 조사로 발견하지 못한 이유와 후속 판정 기준

이전 전체 조사는 원문 취득·추출·분류와 기존 사전 조회를 중심으로 했다. JP 추출 조건이
두 원문을 버린 것은 아니다. 이미지 안의 글자는 문자열 추출 대상이 아니며, 제목·숫자·개행을
조합한 최종 TMP 값은 단독 literal의 조회 성공과 별개다. 따라서 crawler 보완 완료를
전체 화면 번역 완료로 읽히게 설명한 것은 충분히 명확하지 않았다.

후속 조사에서는 아래 세 상태를 별도로 기록한다.

1. **source collected**: 원문/raw와 위치를 확보했는가.
2. **lookup matched**: 실제 전달될 완성 문자열을 기존 조회 함수에 넣었을 때 번역되는가.
   부분 제목만 조회했다면 완성 문자열의 coverage로 올리지 않는다.
3. **native display verified**: 설치한 동일 수정본으로 해당 화면·상태를 실제 확인했는가.
   image는 이름/크기/consumer 확인과 PNG 검수, 실제 표시 확인을 분리한다.

이번 문제의 완성 문자열과 보호 경계는 기존 C# 회귀에 추가했다. 다음 동일 유형의 변경은
숫자 조합·image consumer까지 확인하고, 미확인 화면을 완료 수에 포함하지 않는다.
전체 게임의 모든 runtime 조합이나 모든 이미지 속 글자를 조사했다는 뜻은 아니다.

## 검증 및 적용 상태

- 기존 기준선과 수정본을 같은 UI 사전으로 비교: 숫자 완성 문자열 10표본은 조회 0→10,
  단독 제목/고정 문구 5개는 모두 기존부터 조회 성공.
- 숫자 조합 경계·CRLF/LF·exact 우선·검수 사전 필수·입력창/Novel 보호 회귀 통과.
- Python 87개, C# 4개 프로젝트와 package manifest/hash 검증 통과.
  최초 sandbox 실행에서는 기존 hardlink 회귀의 권한 오류가 있었고, 허용된 환경에서 재실행해 통과했다.
- DLL Release 빌드: 오류 0, 기존 경고 8. 이미지 철자·투명 배경·원본 크기와 작은 크기 확인.
- 현재 단계는 **별도 브랜치의 수정본**이다. 실제 게임 설치·전투 실기·main 병합·릴리스는 하지 않았다.
  다른 작업 폴더의 진행 중인 설정 UI 소스와 설치 DLL을 덮어쓰지 않았다. 향후 두 변경을 통합해
  DLL을 다시 빌드하고 대표 전투 화면을 확인해야 한다.
- UI/Master/Names/Novel 텍스트 정본과 Knowledge는 변경하지 않았다. raw·추출 실패 근거는
  유지했고 이번 추적 결과는 Git 제외 `work/battle-ui-20261103/`에 추가 보존했다.
